## WebGPU and ray tracing

The published WebGPU API defines programmable compute pipelines alongside rendering. As reviewed on the date above, it does not define a standard acceleration-structure/ray-query interface that Harbor can use to request dedicated hardware ray traversal. The GPUWeb working group's issue #11053, opened on 2026-10-13, is explicitly investigating acceleration structures for future ray-tracing/ray-query support. This is an evolving standards area, so recheck the specification before changing that assumption. Sources: [WebGPU specification](https://www.w3.org/TR/webgpu/), [GPUWeb acceleration structure investigation](https://github.com/gpuweb/gpuweb/issues/11053).

The implementation consequence is direct: Harbor builds a triangle BVH on the CPU and traverses it in ordinary WGSL compute shaders. GPU compute can implement real geometric ray intersections and multi-bounce light transport without a dedicated ray-query API. It does not follow that Harbor controls or benefits from hardware RT cores. Browser path tracing also does not automatically provide real-time performance, noise-free output, full physically accurate materials, or commercial-engine feature parity.

The path tracer's rays intersect world geometry, including geometry outside the current image, and accumulate stochastic indirect lighting over repeated samples. Screen-space reflection, shadow maps, and bloom in a raster view are distinct techniques and are not reported as path tracing. The raster renderer remains useful for interactive development and browser coverage while tracing functionality matures.

## Implemented quality renderer dependency

Harbor integrates **three-gpu-pathtracer 0.0.27**, npm source commit [`afc7db6294c15185752b22abc553d17168aaae9b`](https://github.com/gkjohnson/three-gpu-pathtracer/tree/afc7db6294c15185752b22abc553d17168aaae9b), under MIT, © 2021 Garrett Johnson. This version includes a native WebGPU entry; treating it as a WebGL-only library would be incorrect. It accepts Three scenes and provides a wavefront renderer, texture atlas, standard/physical material interpretation, environment importance sampling, physical cameras, and explicit scene-update methods. The implementation is reused through an adapter rather than copied into the simulation core. [WebGPU implementation](https://github.com/gkjohnson/three-gpu-pathtracer/blob/afc7db6294c15185752b22abc553d17168aaae9b/src/webgpu/WebGPUPathTracer.js), [WebGPU API](https://github.com/gkjohnson/three-gpu-pathtracer/blob/afc7db6294c15185752b22abc553d17168aaae9b/src/webgpu/API.md), [license](https://github.com/gkjohnson/three-gpu-pathtracer/blob/afc7db6294c15185752b22abc553d17168aaae9b/LICENSE).

The source uses `SkinnedMeshBVH` when rebuilding skinned content, while `updateTransforms()` updates world matrices and resets accumulation. That is evidence of an upstream deformation path, not evidence that Harbor's actor mixer automatically synchronizes every skinned/morph asset or that continuous updates are fast. Geometry BVH preparation is synchronous. Harbor exposes the native API and keeps these update costs explicit; the validation record identifies the actual exercised paths.

The renderer exposes optional OIDN denoising and FSR upscaling adapters. Its OIDN interface receives the external initializer and weight URL from the caller instead of loading them as default dependencies. This is a useful integration boundary: ship locally licensed model files and measure quality/memory costs before enabling a new mode. Harbor exports these integration points but has not bundled weights or validated denoising. A denoised still image would not, by itself, establish temporal stability during gameplay. [Upstream integration contracts](https://github.com/gkjohnson/three-gpu-pathtracer/blob/afc7db6294c15185752b22abc553d17168aaae9b/src/webgpu/API.md).

## Why these boundaries

- A CPU-only simulation package lets an AI validate game logic, content, deterministic command sequences, and real Rapier collision behavior on the current GPU-less workstation.
- Reusing the upstream quality renderer provides textures, physical materials, HDR lighting and camera infrastructure without rebuilding those systems. The compact custom tracer remains a smaller reference for triangle/BVH experiments and explicit algorithm tests.
- The Three.js/TSL raster view retains an accessible authoring ecosystem and WebGL2 option without coupling the core to browser globals. Three documents its WebGPU renderer and fallback design in [the official WebGPURenderer reference](https://threejs.org/docs/pages/WebGPURenderer.html).
- Physics runs through the modular JavaScript/WASM Rapier library. Character motion is a controller over collisions rather than an assumed ground height; its limitations still require application testing. See [Rapier's JavaScript character controller guide](https://rapier.rs/docs/user_guides/javascript/character_controller/).
- Declarative scenes, stable IDs, strict validation, explicit plugin lifetimes, and machine-readable CLI results reduce the amount of context another AI needs before changing a game.

These are engineering judgments based on the inspected code and current goals. They are not a claim that the two reference repositories already solve arbitrary game development, or that rewriting all rendering infrastructure necessarily improves performance.

## Additional references

The following projects were subsequently requested as design references. Their features are not automatically Harbor features. The goal is to reduce repeated game-development work through small reusable interfaces while preserving the current core and rendering boundaries.

### PlayCanvas

Reviewed engine snapshot: [`342ec1a04585928918d60fea1af900fbfec3cb7a`](https://github.com/playcanvas/engine/tree/342ec1a04585928918d60fea1af900fbfec3cb7a), dated 2026-10-18 and labelled `2.24.0-beta.15` on the reviewed main branch. This is a source snapshot, not a statement about the latest stable release. Reviewed Editor frontend: [`50da536f25745eb7e66101a8bf4088d12f4a271e`](https://github.com/playcanvas/editor/tree/50da536f25745eb7e66101a8bf4088d12f4a271e).

PlayCanvas is particularly useful as a reference for the engine services surrounding rendering:

- **Backend selection and truthful diagnostics.** Its device factory tries requested devices in order and adds WebGL2 as a fallback. A null device is opt-in and draws nothing. Harbor can adopt the same clarity about requested versus actual capabilities without replacing its existing Three view or compute tracer. [Device factory](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/platform/graphics/graphics-device-create.js).
- **Component lifetimes.** Components expose enable/disable behavior; systems expose creation and removal events. The reviewed implementation also warns about unknown component options in debug builds, with those warnings removed from release builds. This suggests a future typed component registry and explicit activation hooks; Harbor's existing strict scene validator should remain authoritative. [Component](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/framework/components/component.js), [component system](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/framework/components/system.js).
- **Asset organization.** AssetRegistry indexes asset metadata and separates registration from loading; BundleRegistry resolves asset URLs from explicitly loaded/loading bundles. Useful follow-ups for Harbor are manifests, dependency-aware preload groups, progress, and residency budgets while retaining independent reference-counted ownership. [Asset registry](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/framework/asset/asset-registry.js), [bundle registry](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/framework/bundle/bundle-registry.js).
- **Compression capabilities.** The official engine documents glTF, Draco, and Basis support. Its reviewed KTX2 parser specifically routes Basis/ETC1S/UASTC content to a transcoder and still marks other uncompressed KTX2 handling as unfinished. This is a useful model for explicit decoder capabilities and local decoder packaging, not a reason to claim universal format support. [Engine features](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/README.md), [KTX2 parser](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/src/framework/parsers/texture/ktx2.js).
- **Batch budgets and invalidation.** Batches group compatible materials, shader parameters, layers, and spatial bounds. Maximum AABB size balances draw-call reduction against culling; rebatching is explicitly expensive. Harbor can refine its existing spatial batches and dirty updates using these rules. [Official batching guide](https://developer.playcanvas.com/user-manual/graphics/advanced-rendering/batching/).
- **Optional splat streaming.** Streamed SOG uses spatial regions, multiple detail levels, loading/unloading, and a global splat budget, with distance/error selection and field-of-view considerations. Its budget/residency policy is worth studying for a future streaming module. This evidence concerns splat LOD, not automatic LOD generation for every mesh. [Streamed SOG](https://developer.playcanvas.com/user-manual/gaussian-splatting/building/lod-streaming/).

The official splat renderer documentation identifies rasterization with CPU-worker sorting or WebGPU GPU sorting. GPU sorting and Gaussian splatting are not multi-bounce path tracing. The reviewed sources do not establish a general PlayCanvas path-tracing renderer for Harbor to reuse, so this review makes no such claim. [Splat rendering pipelines](https://developer.playcanvas.com/user-manual/gaussian-splatting/rendering-architecture/renderers/).

Both the engine and the Editor frontend source carry MIT licenses. The Editor README's local-development flow still connects a locally built frontend to a hosted PlayCanvas scene/account. The frontend's license therefore should not be described as a complete self-hosted backend or as the terms of the hosted service. The Editor also links an MCP integration, which is a useful reference for explicit AI inspection/edit commands; Harbor does not currently ship that integration. [Engine license](https://github.com/playcanvas/engine/blob/342ec1a04585928918d60fea1af900fbfec3cb7a/LICENSE), [Editor license](https://github.com/playcanvas/editor/blob/50da536f25745eb7e66101a8bf4088d12f4a271e/LICENSE), [Editor development and MCP notes](https://github.com/playcanvas/editor/blob/50da536f25745eb7e66101a8bf4088d12f4a271e/README.md).

### LOD and streaming as separate capabilities

Three's `LOD` selects authored object levels by distance; it does not create simplified meshes or stream a world. Meshoptimizer/glTF Transform can prepare lower-detail assets offline, but simplification and quantization change content and need explicit error budgets. The standalone `gltfpack` pipeline also strips or restructures some metadata by default, so it should not replace Harbor's conservative preservation command without an asset-specific profile. [Three LOD](https://threejs.org/docs/pages/LOD.html), [gltfpack options and supported extensions](https://github.com/zeux/meshoptimizer/blob/v1.3/gltf/README.md).

A possible Harbor module would combine asset handles, distance/error budgets, loading groups, and explicit release rules, drawing on PlayCanvas's registry/streaming designs above. Geometry/LOD swaps must also invalidate the tracing scene correctly. This is a proposed extension, not an implemented streaming system; target-device memory and rebuild costs should determine its design. It should remain independent of the CPU world core.

### Offline asset tooling and optional navigation

Harbor reuses **glTF Transform 4.5.1** (`@gltf-transform/core` and `extensions`, MIT), **meshoptimizer 1.3.0** (MIT), and the official **Khronos glTF Validator 2.0.0-dev.3.10** (Apache-2.0) as development tools. glTF Transform is Don McCurdy's independent project; glTF and its validator are Khronos projects. The SDK supports Node.js and can read assets without enabling network access. The full glTF Transform CLI offers additional transforms, but its general optimization defaults include changes such as quantization, hierarchy flattening, merging, simplification, and texture conversion that should be chosen deliberately for authored game content. [glTF Transform SDK](https://github.com/donmccurdy/glTF-Transform/tree/v4.5.1), [CLI and options](https://gltf-transform.dev/cli), [meshoptimizer](https://github.com/zeux/meshoptimizer/tree/v1.3), [Khronos validator](https://github.com/KhronosGroup/glTF-Validator).

The implemented `tools/assets.ts` preserves the original glTF JSON graph and compresses suitable numeric buffer views with Meshopt's lossless codecs. It uses `INDICES` rather than the triangle codec to retain exact corner order, applies no lossy filters, and validates decoded bytes and interpreted accessors before publishing a new file. This makes metadata preservation explicit instead of assuming an SDK round-trip preserves every storage-level field. Unknown extensions and already compressed inputs are rejected for optimization. Geometry decoding precedes GPU upload: delivery compression alone is not a draw-call or rendering-speed optimization. [Meshopt extension specification](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Vendor/EXT_meshopt_compression/README.md), [SDK Meshopt implementation](https://github.com/donmccurdy/glTF-Transform/blob/v4.5.1/packages/extensions/src/ext-meshopt-compression/meshopt-compression.ts).

**KTX2/Basis is a separate optional texture pipeline.** KTX2 is a Khronos container; Basis Universal supplies texture codecs and transcoders. The reviewed latest releases were KTX-Software **4.4.2** and Basis Universal **2.50**. Native tools and WebAssembly enable CPU-only offline encoding. The glTF Transform 4.5.1 texture adapter invokes `ktx create` and requires KTX-Software 4.4.0 or newer. The encoder's success does not establish a browser decoder's support for every new format: classic ETC1S/UASTC and newer HDR/XUASTC/XUBC7 modes must be checked against the chosen runtime. Harbor's default asset loader does not yet configure a KTX2 transcoder, so its optimization command does not emit KTX2. [KTX-Software releases](https://github.com/KhronosGroup/KTX-Software/releases/tag/v4.4.2), [Basis Universal 2.50](https://github.com/BinomialLLC/basis_universal/releases/tag/v2_50), [glTF Transform KTX adapter](https://github.com/donmccurdy/glTF-Transform/blob/v4.5.1/packages/cli/src/transforms/toktx.ts).

KTX-Software's own source is generally Apache-2.0 and Basis Universal's reference implementation is Apache-2.0, with bundled third-party files carrying additional notices. In particular, KTX-Software identifies a non-open-source ETC fallback decoder that can be excluded from builds; a redistributed binary needs an audit of the actual enabled components, not a blanket license label for the entire repository. These encoders are researched options, not bundled Harbor dependencies. [KTX license inventory](https://github.com/KhronosGroup/KTX-Software/blob/v4.4.2/LICENSE.md), [Basis license](https://github.com/BinomialLLC/basis_universal/blob/v2_50/LICENSE).

**Recast Navigation JS 0.43.1** is a possible optional navigation module, not a core dependency. It wraps Recast/Detour in WebAssembly, supports Node.js and browsers, and provides solo/tiled mesh generation, path queries, crowds, temporary obstacles, and serialized navmeshes. Static levels can be baked offline and loaded at runtime; larger levels can use tiled generation. Worker examples require application-owned workers, and the project explicitly notes that not all native APIs are exposed. The JavaScript wrapper is MIT; native Recast/Detour uses the zlib license. Any future Harbor integration should own its WASM resources per world, separate baking from runtime queries, and feed movement through the physics controller rather than assuming navigation replaces collision. No navigation feature is claimed in this alpha. [Project and Node/offline workflows](https://github.com/isaac-mason/recast-navigation-js), [wrapper license](https://github.com/isaac-mason/recast-navigation-js/blob/main/LICENSE), [native license](https://github.com/recastnavigation/recastnavigation/blob/main/License.txt).

## Validation and platform research limits

Production-readiness evidence must be separated into CPU behavior, shader correctness, rendered-image behavior, and real-device measurements. Passing a software WebGPU test establishes only the checks actually exercised by that adapter and scene. New mobile, laptop, and desktop tests should record browser/version, adapter, render resolution, triangle count, bounce count, samples, elapsed time, and observed error/device-loss behavior.

The initial output is a static web build with relative URLs and optional browser storage. Bilibili Toy and VibeHub were requested as potential distribution destinations. No platform certification or authenticated upload is implied by the generic export. Their current upload formats, iframe GPU permissions, size limits, SDK APIs, and account terms need verification against the selected host before integration is claimed. Keep that integration in a game/platform adapter rather than making it an engine-core dependency.
